# 数据库实施文档

## 1. DBMS 版本与配置选择

本系统选用 **MySQL 8.0+(实测兼容 9.x)** 作为数据库管理系统。MySQL 8 是当前生产环境最广泛使用的关系数据库,其生态、文档与运维工具最为成熟,同时完整支持触发器、存储过程、游标、CHECK 约束、JSON 函数、全文索引、窗口函数等本系统所需的全部高级特性。开发与测试均在 MySQL 9.6 环境下完成,但 DDL 脚本严格遵循 8.0 语法,可在 5.7 之外的所有现代 MySQL 实例上运行。

服务端配置上,使用 InnoDB 作为默认存储引擎,以支持事务、行级锁与外键约束;字符集与排序规则统一采用 utf8mb4 / utf8mb4_0900_ai_ci,保证中文、emoji、生僻字均可正确存储与排序;`innodb_default_row_format=DYNAMIC` 以支持长 VARCHAR 与 TEXT 字段;`max_allowed_packet` 建议至少 64 MB 以支持大型 JSON 字段与 MEDIUMTEXT 块。开发期 `sql_mode` 保留 STRICT_TRANS_TABLES,从而让任何越界的字段写入立即报错而非被截断。

## 2. 字符集与排序规则选择理由

字符集选用 utf8mb4 而非旧版 utf8(实际为 utf8mb3)是为了完整支持 4 字节 Unicode 字符,如表情符号、汉字扩展 B 区、罕用字符等。排序规则选用 utf8mb4_0900_ai_ci 是 MySQL 8 引入的基于 Unicode 9 的不区分大小写、不区分重音的排序;它对中文字符按 Unicode 码位排序,保证 ORDER BY 中文字段时结果稳定;对英文按字母不区分大小写,符合用户直觉。如果未来需要按拼音排序,可在中文字段上叠加生成列存储拼音首字母再按 ASCII 排序。所有表与列均显式声明 `DEFAULT CHARSET=utf8mb4`,避免误用服务器默认值。

## 3. DDL 实施顺序与依赖

数据库的初始化按以下严格顺序执行,任何乱序都会因外键缺失或对象不存在而报错:

- **00_drop_all.sql**:按依赖反向 DROP 全部对象,用于重置环境。
- **01_schema.sql**:创建 12 张主表 + 2 张 RAG 预留表,所有 FK 在表定义中即声明,要求父表先于子表创建。例如 users 必须先于 topics,topics 先于 documents,documents 先于 document_chunks 与 cognitive_maps,entities 先于 entity_aliases、relationships、chunk_entity_mapping。
- **02_indexes.sql**:在主表创建完成后建立 7 个二级索引 + 2 个 RAG 索引,共 9 个,放在独立文件便于性能实验时单独 DROP/CREATE。
- **03_views.sql**:创建 3 个视图,依赖于实体、关系、主题、任务等表。
- **04_triggers.sql**:5 个触发器,依赖于 documents、document_chunks、entities、relationships、chunk_entity_mapping 等表与 audit_logs。
- **05_procedures.sql**:6 个存储过程,部分过程内部使用临时表与游标,要求 DELIMITER 切换。
- **06_seed.sql**:演示数据(3 用户 / 2 主题 / 4 文档 / 15 实体),供 UI 演示。
- **07_seed_perf.sql**:性能压测数据(约 50K chunks、10K entities、30K relationships、50K mappings),仅在性能实验时加载。

`Makefile` 中 `db-init` 目标按 01→02→03→04→05 的顺序逐文件 source,`db-reset` 则先 drop 后 init 再 demo-load,确保任何回归都可一键复现。

## 4. 数据类型选型

主键统一使用 BIGINT AUTO_INCREMENT,而非 INT。理由是 BIGINT 提供 19 位有符号范围,完全杜绝主键溢出;在 64 位现代 CPU 上 BIGINT 与 INT 的存储和运算开销基本相当,代价可忽略。文本字段按长度选择 VARCHAR / TEXT / MEDIUMTEXT:用户名、邮箱等短串使用 VARCHAR(64/128/255);文档与块内容使用 MEDIUMTEXT(16 MB 上限),同时为大型 PDF 解析结果留出冗余。结构化扩展属性使用 JSON 而非 TEXT,从而能利用 MySQL 8 的 `->`、`->>`、JSON_EXTRACT、JSON_OBJECT 等原生函数。枚举字段如 role、status、source、entity_type 一律使用 ENUM,以最小代价换取数据库层的取值校验。哈希列(content_hash)使用 CHAR(64) 严格匹配 SHA-256 长度。RAG 向量字段使用 LONGBLOB 存储 float32 紧凑数组(详见第 6 节)。weight 等比例字段使用 DECIMAL(4,3) 避免浮点累加误差。时间字段统一 DATETIME + DEFAULT CURRENT_TIMESTAMP + ON UPDATE CURRENT_TIMESTAMP,从数据库层而非应用层维护时间戳。

## 5. 完整性约束体系

本系统在 schema 层面构建了完整的约束体系:**主键(PK)** 全部使用代理键 BIGINT;**外键(FK)** 全部显式定义,并按业务语义选择 ON DELETE CASCADE / RESTRICT / SET NULL;**唯一约束(UQ)** 表达业务唯一性,如 (owner_id, name)、(topic_id, entity_type, canonical_name)、(entity_id, alias);**CHECK 约束** 防止业务非法值,如 relationships 的 `source <> target`;**NOT NULL** 用于所有不可缺省字段;**DEFAULT** 配合 CURRENT_TIMESTAMP 自动维护时间戳;**ENUM** 在数据库层校验枚举取值。这套约束体系使得即便应用层存在 bug,数据库依然能拒绝大多数非法写入,极大降低了数据腐烂风险。

## 6. RAG 表设计决策

RAG 预留表 chunk_embeddings 与 entity_embeddings 的 embedding 字段使用 LONGBLOB 而非 JSON 或 VECTOR,理由如下。第一,MySQL 8.0 没有原生 VECTOR 类型,9.x 才引入,本系统目标兼容 8 版本。第二,JSON 数组形式存储一个 1024 维 float 向量,每维都要保留 ASCII 数字与分隔符,平均消耗 80 KB,而 LONGBLOB 中 float32 紧凑存储仅 4 KB,节省 20 倍空间和 IO。第三,LONGBLOB 上层易于序列化(numpy `tobytes()`)和反序列化(`np.frombuffer`),计算余弦相似度时可直接 SIMD 加速。第四,本期不实现 ANN 检索,LONGBLOB 不利于人工排查的劣势可接受;未来若升级到原生 VECTOR,只需 ALTER 列类型并配上 HNSW/IVF 索引即可。这些权衡详见 `docs/superpowers/specs/2026-05-07-nkg-design.md` 第 12.1 节。

## 7. Migration 策略

本期采用 **drop_all + 分步重建** 的简单 migration 策略,适合课程作业场景。`sql/00_drop_all.sql` 负责按反向依赖顺序 DROP 全部对象,所有 DDL 脚本均设计为幂等可重入(IF EXISTS、IF NOT EXISTS、OR REPLACE),反复执行不会报错。这种"全量 drop + 全量 init"的做法在数据量较小、变更频繁的开发期最为高效;当系统进入生产期,可平滑切换到 Flyway / Liquibase 等版本化迁移工具,以保留历史数据。

## 8. 备份与恢复建议

建议每日凌晨低峰期执行一次全量逻辑备份,命令如下:

```bash
mysqldump -u root -p \
    --single-transaction \
    --routines --triggers --events \
    --default-character-set=utf8mb4 \
    nkg > nkg_$(date +%F).sql

# 恢复
mysql -u root -p nkg < nkg_2026-05-07.sql
```

`--single-transaction` 保证 InnoDB 一致性快照,不锁表;`--routines --triggers --events` 同时备份存储过程、触发器与事件;`--default-character-set` 防止中文乱码。生产环境建议加上 binlog 增量备份,实现 PITR(point-in-time recovery)。压测数据集可单独导出,通常仅在性能实验时使用,避免每日备份膨胀。

对于本课程作业的演示与答辩场景,推荐保留两份基线:一份是仅 schema 与演示数据的版本,文件较小,可用于快速搭建答辩环境;另一份是包含完整压测数据的版本,用于复现性能实验数据。两份基线均纳入版本控制目录,任何同学按 README 步骤执行 `make db-reset` 即可在本地一键复现完整数据库状态,保证实验的可复现性与可审计性。
