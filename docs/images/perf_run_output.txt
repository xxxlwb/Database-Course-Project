-- ============================================================
-- NOTES on observed behavior (added post-run; SQL was NOT modified):
-- ============================================================
-- Exp 1: DROP failed with ERROR 1553 because idx_relationships_src_dst_type
--   is the only index whose leftmost column is source_entity_id, so the FK
--   constraint requires it. The "no-index" baseline could not be measured;
--   with the index the lookup is ~0.027ms (cost=0.869, 1 row).
--
-- Exp 2: DROP failed with ERROR 1553 for the same reason --
--   idx_mapping_entity covers the FK on entity_id and cannot be dropped.
--   With the index the lookup is ~0.03-0.44ms (cost=1.75, 5 rows).
--
-- Exp 3: LIKE '%keyword-7%' did a full table scan
--   (rows=50008, time=58ms). MATCH ... AGAINST used ft_chunks_content
--   FULLTEXT (rows=50000, time=46.9ms). The seed data places "keyword-7"
--   in ~every chunk, so both return ~all rows -- the FULLTEXT advantage
--   would be larger on a more selective term, but the plan still shows
--   the FULLTEXT index lookup vs a table scan, which is the intended
--   demonstration.
--
-- Exp 4: Without topic_id the optimizer chose a table scan
--   (cost=1119, rows=10233) because entity_type is NOT the leftmost
--   column of idx_entities_topic_type_name(topic_id, entity_type, ...).
--   With topic_id added, MySQL switched to an index lookup using
--   uq_entity_topic_type_name (the UNIQUE composite covering the same
--   prefix), cost=412, rows=1256 -- demonstrating leftmost-prefix usage.
