# 操作手册

本手册帮助管理员与终端用户在本地或 Docker 环境下完成 NKG 系统的部署、配置、日常使用与故障排查。完整使用示例与界面截图请参考 README 与 docs/images/ 目录,本手册侧重命令行操作与运维注意事项,确保任何具备基础 Unix 运维经验的同学都可以独立完成搭建与日常维护。

## 1. 系统要求

| 项 | 最低要求 | 推荐 |
|---|---|---|
| 操作系统 | macOS 12 / Ubuntu 20.04 / Windows 10 + WSL2 | 任意 64 位 Unix-like |
| MySQL | 8.0 | 9.x |
| Python | 3.11 | 3.11.x |
| Node.js | 18 | 20 LTS |
| 内存 | 4 GB | 8 GB(含 LLM 缓存) |
| 磁盘 | 1 GB | 10 GB(含压测数据) |

如果选择 Docker 部署,则只需 Docker 24+ 与 docker compose 插件。

## 2. 安装步骤(本地 MySQL 路径)

第一步,准备数据库实例。在已经安装 MySQL 8.0 或更高版本的机器上,创建数据库并赋权:

```bash
mysql -u root -p -e "
CREATE DATABASE nkg DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'nkg'@'%' IDENTIFIED BY 'nkg';
GRANT ALL PRIVILEGES ON nkg.* TO 'nkg'@'%';
FLUSH PRIVILEGES;
"
```

第二步,克隆仓库并写入配置:

```bash
git clone <repo-url> db_course && cd db_course
cp .env.example .env   # 编辑数据库密码、JWT 密钥、MiniMax API key
```

第三步,初始化 schema、视图、索引、触发器、存储过程,以及演示数据:

```bash
make db-init           # 顺序执行 01_schema → 02_indexes → 03_views → 04_triggers → 05_procedures
make demo-load         # 加载 06_seed.sql,即 3 用户 / 2 主题 / 4 文档 / 15 实体
```

如需运行性能实验,再执行 `make perf-load`,加载 `07_seed_perf.sql` 的五万行压测数据。

## 3. 安装步骤(Docker MySQL 路径)

如果不希望本机安装 MySQL,可使用 docker-compose 一键启动 MySQL 8 + Adminer:

```bash
docker compose up -d mysql adminer    # MySQL 监听 3306,Adminer 在 http://localhost:8080
docker exec -i nkg-mysql mysql -uroot -proot < <(echo "
  CREATE DATABASE nkg DEFAULT CHARSET utf8mb4;
  CREATE USER 'nkg'@'%' IDENTIFIED BY 'nkg';
  GRANT ALL PRIVILEGES ON nkg.* TO 'nkg'@'%';
")
make db-init && make demo-load
```

之后的后端、前端启动方式与本地路径一致。

## 4. 配置 .env

`.env` 文件统一管理后端配置,关键项含义如下:

- `DB_HOST / DB_PORT / DB_USER / DB_PASSWORD / DB_NAME`:数据库连接参数,本地默认 127.0.0.1:3306。
- `JWT_SECRET`:JWT 签名密钥,**必须改成至少 32 位随机字符串**,例如 `openssl rand -hex 32` 的输出。
- `JWT_EXPIRE_MIN`:JWT 过期分钟数,默认 1440(一天)。
- `MINIMAX_API_KEY`:MiniMax 大模型 API 密钥,留空则自动启用 mock 模式。
- `MINIMAX_BASE_URL / MINIMAX_MODEL`:模型服务地址与模型名,默认指向 MiniMax 官方端点。
- `LLM_MOCK`:显式开启 mock 模式,true 时即使有 API key 也使用本地规则抽取,适合答辩演示。
- `RAG_ENABLED`:是否启用 RAG 路由(本期默认 false)。
- `SQL_CONSOLE_ENABLED`:是否启用 SQL 控制台,默认 true,生产环境可改为 false 关闭风险入口。

## 5. 启动后端

```bash
cd backend
uv venv && source .venv/bin/activate
uv pip install -e .          # 安装 FastAPI、SQLAlchemy 等依赖
cd .. && make backend        # 等价于 uvicorn app.main:app --reload --port 8000
```

后端启动后,访问 http://localhost:8000/docs 即可看到自动生成的 OpenAPI 接口文档。

## 6. 启动前端

```bash
cd frontend
npm install                  # 也可使用 pnpm 或 yarn
npm run dev                  # 默认在 http://localhost:5173
```

前端开发服务器开启了 vite 热更新,代码变更后页面自动刷新。

## 7. 用户操作流程

打开浏览器访问 http://localhost:5173,即可进入登录页。

- **注册与登录**:首次使用先注册账号,系统默认赋 editor 角色;登录成功后页面跳转到 Dashboard。
- **创建 Topic**:进入"主题管理"页,点"新建主题",填写名称与描述并保存;同一用户下名称不可重复。
- **上传文档**:进入"文档管理"页,选择目标主题并上传文件,支持 .txt / .md / .pdf;后端自动计算 SHA-256 哈希并切块。
- **触发认知地图生成**:在文档详情页点"生成认知地图",后端调用 LLM 生成关键实体、主题、时间线、模式四类信息。
- **触发蓝图生成**:在主题详情的"蓝图"tab 点"生成蓝图",后端聚合该主题下所有文档的认知地图,产出 canonical_entities、key_patterns、global_timeline。
- **触发实体抽取**:同一 tab 下点"抽取图谱",后端基于蓝图与文档块抽取实体与关系并写入数据库。
- **浏览图谱**:在主题详情的"图谱"tab 查看 ECharts force-directed 可视化,支持节点拖拽、搜索、过滤;鼠标悬停查看实体详情,点击节点跳转到实体页。
- **实体合并 / 别名管理**:在"实体库"页选两个同主题实体执行合并,系统调用 sp_merge_entities 自动迁移关系、映射、别名;别名管理面板支持手动新增、删除别名。

## 8. SQL 控制台用法

入口位于左侧导航的"SQL 控制台",**仅 admin 角色可见**。在 Monaco 编辑器中输入单条 SQL,点"执行"。

- `SELECT * FROM topics LIMIT 10;` —— 返回行集,前端以表格形式展示。
- `EXPLAIN ANALYZE SELECT ...` —— 返回计划树,前端以可折叠节点呈现。
- `CALL sp_get_entity_neighborhood(1, 2, @c); SELECT @c;` —— 注意:控制台**只允许单条 SQL**,需要分两次执行。
- `SHOW TRIGGERS;` / `SHOW PROCEDURE STATUS WHERE Db='nkg';` —— 快速查看触发器与存储过程清单。

安全提示:任何 DDL/DROP 操作都会弹二次确认;每次执行写入审计日志;`SET STATEMENT max_statement_time=15` 防止死循环;若被滥用可在 `.env` 中设置 `SQL_CONSOLE_ENABLED=false` 一键关闭。

## 9. 维护操作

进入"系统设置"页(admin),提供以下批量维护按钮:

- **重算 mention_count**:调用 `sp_recompute_entity_mentions()`,游标遍历所有实体并基于 chunk_entity_mapping 重算其提及次数,用于反规范化字段的修复。
- **归档过时主题**:调用 `sp_archive_inactive_topics(?, @count)`,游标遍历指定天数内未更新的主题并标记 is_archived=1,通过 OUT 参数返回归档总数。
- **批量改名**:调用 `sp_propagate_entity_rename(?, ?, ?)`,游标遍历主题内匹配 LIKE 模式的实体,旧名自动加入别名表,然后执行 UPDATE IGNORE 改名。

每次执行均自动写入 audit_logs,可在审计页面查看。维护操作建议在系统负载较低的时间段执行,以避免锁争用与长事务。

## 10. 故障排查 FAQ

- **MySQL 连接失败**:检查 `.env` 中 DB_HOST / DB_PORT / DB_USER / DB_PASSWORD 是否正确;运行 `mysql -u nkg -p -h 127.0.0.1` 手动验证。Docker 部署需要确认容器已启动且端口未被占用。
- **MiniMax LLM key 缺失**:.env 中 `MINIMAX_API_KEY` 留空时系统自动回退 mock 模式,前端会在抽取按钮旁显示"mock"标签;若需真实 LLM,请前往 MiniMax 控制台申请 key 并填入。
- **前端 npm install 失败**:多见于网络问题,可改用国内镜像 `npm config set registry https://registry.npmmirror.com`;Node 版本需要 18+。
- **触发器/存储过程未生效**:运行 `make db-reset` 重置全部对象;Docker 路径下需重启容器再执行。
- **测试报错 access denied**:确认数据库用户权限,推荐使用 root 或 nkg 用户运行测试,避免 GRANT 不足。
- **图谱页面卡顿**:节点超过 1000 时建议在过滤栏选择更窄的实体类型或度阈值;ECharts 默认布局对超大图谱不友好,可考虑后续接入 GraphIn。
- **build 失败**:前端构建失败常见原因是 TypeScript 严格模式的隐式类型错误,可通过 `npm run build -- --mode development` 暂时跳过严格检查;真正的部署构建建议修复后再发布。
- **审计日志膨胀**:audit_logs 表会随使用持续增长,建议每月归档至冷存储或按时间分区;具体分区策略可参考 MySQL 官方文档中的 RANGE 分区方案,本期未启用以保持 DDL 简洁。
- **JWT 过期**:默认 24 小时过期,前端检测到 401 自动跳转登录;长会话场景可调整 JWT_EXPIRE_MIN 或后续接入 refresh token 机制,本期未实现以保证课程评分相关代码量可控。
