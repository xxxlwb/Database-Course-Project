# 测试报告

## 1. 测试范围

本次测试覆盖系统从底层 schema 到上层 API 的全部关键路径,共 7 个维度:

- **单元测试**:核心 service 函数与安全模块函数(密码哈希、JWT 编解码)。
- **集成测试**:API 端到端,包含注册、登录、Topic CRUD、实体 CRUD、合并等业务流。
- **触发器测试**:针对 5 个触发器各设计专项用例,断言其副作用确实发生。
- **存储过程测试**:针对 6 个存储过程逐个调用,覆盖 IN/OUT 参数、游标遍历、临时表、事务回滚等所有特性。
- **性能测试**:针对 7 个二级索引在五万行规模数据集上做 EXPLAIN ANALYZE,详见 `docs/07-性能分析实验.md`。
- **事务测试**:针对实体合并的多表迁移场景,验证任何步骤异常都能完整回滚。
- **安全测试**:SQL 控制台拒绝多语句拼接、JWT 鉴权依赖、bcrypt 哈希一致性。

测试设计遵循"金字塔"原则,底层是大量快速的单元测试,中层是覆盖业务流的集成测试,顶层是少量针对触发器和存储过程的端到端验证。每一类用例都有清晰的断言目标,而非简单"跑通即过"。例如触发器测试不仅插入数据,还要在插入后立刻 SELECT 计数字段、审计日志、状态字段,逐一断言其变化符合预期。这种"行为驱动"的测试风格让回归一旦发生即可定位到具体的功能缺口。

## 5. 性能测试摘要

性能测试在五万行 chunks、一万行 entities、三万行 relationships、五万行 mappings 的压测数据集上进行,使用 EXPLAIN ANALYZE 命令逐个观察执行计划与实际耗时。完整数据见 `docs/07-性能分析实验.md`,以下为四段实验的核心结论。

- **实验 1**:`idx_relationships_src_dst_type` —— 因外键依赖无法 DROP,仅记录索引存在时的查询性能 0.027 ms,执行计划走 Index lookup,cost=0.869,扫描 1 行。
- **实验 2**:`idx_mapping_entity` —— 同样因外键依赖无法 DROP,索引存在时查询 0.029-0.44 ms,Index lookup,cost=1.75,扫描 5 行。
- **实验 3**:`FULLTEXT vs LIKE` —— LIKE '%keyword-7%' 全表扫描,扫描 50008 行,耗时 58 ms;MATCH ... AGAINST 走 ft_chunks_content,cost 仅 0.35,虽然返回 50000 行(因测试种子 keyword-7 选择性低),但执行计划已显示 FULLTEXT 路径,验证了索引可用性。
- **实验 4**:复合索引最左前缀 —— 仅按 entity_type 过滤回退到全表扫描(cost=1119,rows=10233);加入 topic_id 后命中 uq_entity_topic_type_name 复合索引(cost=412,rows=1256),证明最左前缀规则。

实验结果整体证明二级索引设计有效,符合关系数据库索引选型与最左前缀的经典原则。

性能测试同时验证了一个有趣的现象:即便我们想做"无索引基线"对照,InnoDB 的外键完整性约束也会强制保留底层索引,使得 DROP INDEX 直接失败。这从侧面证明了 MySQL 对引用完整性的严格保护,也提示了在设计性能实验时需要将外键依赖纳入考虑。这一发现已在性能分析文档与本测试报告中均明确记录,作为课程实验中"不可避免的限制条件"的真实呈现。

## 6. 缺陷与遗留

测试过程中识别出若干已知限制,均在文档中明确说明,不视为代码缺陷:

- **FK 隐式索引依赖**:idx_relationships_src_dst_type 与 idx_mapping_entity 同时是外键所要求的索引,因此 `ALTER TABLE ... DROP INDEX` 会被 MySQL 以 `ERROR 1553` 拒绝。这意味着无法在不破坏外键的前提下做"无索引基线"对照。文档中明确承认这一现象,只记录索引存在时的实际查询计划与耗时。
- **FULLTEXT keyword-7 高命中率**:压测种子脚本以 `chunk-{i} keyword-{i%10}` 模式生成 50K 条文本,故 keyword-7 在五万条中命中约五千条,选择性极低,导致 FULLTEXT 与 LIKE 在数据返回量上差距不显著。但执行计划上的 Full-text index search vs Table scan 仍然清晰可见,符合"演示索引可用性"的目标。
- **passlib DeprecationWarning**:passlib 1.7 的 crypt 后端在 Python 3.13 中将不可用,本项目运行在 3.11.14,不受影响,后续可平滑切换到 argon2 或自定义 bcrypt 调用。
- **LLM mock 模式**:为保证脱网演示,llm.py 在缺失 API key 时回退到本地规则抽取,因此抽取出的实体与关系是确定性的、不带语义噪声的,真实部署时质量与 LLM 模型能力强相关。
- **SQL 控制台限制**:仅允许单语句执行,不支持批处理与脚本上传,这是有意的安全设计;如需批量初始化请使用 `make db-init` 等命令行工具。
- **测试数据规模**:为保证测试快速反馈,demo 数据集仅几十条记录;真实生产场景下的极端规模(百万级实体、千万级关系)未纳入回归集,需要单独压测。
- **未覆盖的浏览器端测试**:本期仅覆盖后端与 SQL,前端 13 个页面的交互测试由人工跑过完整 demo 路径并截图存档,自动化的 Playwright 测试列入未来工作,本期通过详细操作截图清单弥补覆盖缺失。
